## 结论

完成 **17 个合成资源场景**及每项后的基线恢复。36 次主配置阴性检查均通过，显式同配置加载的阳性对照通过，恢复原引用后的阴性复核通过。因此，本机本版本下，这批单资源更新没有把磁盘中的主配置见证加载进运行状态。

下载失败会保留旧资源，但 **命令退出 0、ready=true 均不足以证明成功**。混合坏节点会部分接受，重复名称会接受第一条；必须在发布前严格验证完整内容，并在发布后读回目标成员、实际参数和链路，不能只相信 success。

后台 HTTP、长流、WebSocket 没有中断。完整 305 秒 Chrome 观察中有 2 次公网 HTTPS 超时；它们在矩阵更新结束很久之后，与后段全量离线测试重叠，存在负载干扰，不能宣称全程 HTTPS 连续性通过，也不能据此归因 Surge。17 项实际更新期间的 Chrome HTTP/HTTPS 对照均为 30/30 成功。

## 执行记录

前两次启动没有进入矩阵，保留其记录以免把工具问题算成 Surge 结果：

1. 首次同配置加载后立即查资源，登记尚未出现，守卫停止。初版回退重复使用了“资源必须已登记”前提，导致服务暂时保留。随后只读确认资源已唯一登记、无更新在途、文件未漂移，执行独立精确回退并只终止已核对的本次夹具进程；所有端口关闭。修正为有时限的登记等待，回退不再要求未开始更新的资源必须存在。
2. 第二次登记和主配置阴性检查通过，但非交互执行会话关闭了输入，未进入矩阵；finally 自动恢复原引用，全部服务停止。
3. 第三次使用持续交互会话，**12:50:43–12:56:31** 完成矩阵、305 秒观察、阳性对照与回退。17 项及恢复共 34 次定向更新，加初始化 1 次，合计 **35 次单 key 更新**；没有 update all 或对不明确结果重放命令。Surge 自己的下载重试另行计数。

本维护窗口合计 7 次显式同配置加载：前两次启动各接入/回退 2 次，完整运行接入/阳性对照/回退 3 次。没有 restart-engine。动态矩阵阶段没有 reload，也没有继续写主配置或依赖文件。

## 主配置见证

1. 接入加载时仍使用旧见证：旧主机请求经 `p0-canary`，新主机经 `p0-plain`。
2. 自动重载保持关闭，将主配置中的唯一见证行改为新主机，**不加载**。延迟检查仍旧主机经 canary、新主机经 plain。
3. 每个故障更新和基线恢复后分别对两个主机发起新连接请求，以回显服务记录的合成节点身份判断规则是否生效；组选择和进程启动时间只是旁证。
4. 布置后 1 次、17 项各 2 次、动态收尾 1 次，共 **36 次阴性检查**全部通过。38 项外部资源中仅目标 policy-group 的记录发生变化，其余 37 项不变；引擎 startedAt 不变。
5. 停止连续性测量、关闭 Chrome 测试页后，显式同配置加载作为阳性对照：**新主机转为 p0-canary，旧主机转为 p0-plain**，证明见证具有检测能力。
6. 恢复原主配置并加载后，新主机再次经 plain、旧主机再次经 canary。

该结论限定为本机、本版本、合成 policy-group 资源和本次已观察的调用；不是对所有 Surge 内部实现的形式证明。

## 失败和内容矩阵

每项从有效 A/B/C 基线开始。除“删除未选中 C”外，测试前选择 C；所有请求仅访问合成链路主机。每项结束改选 REJECT，恢复有效 A/B/C，执行一次同 key 更新，并用独立策略探测确认 C 经前置到达 `p0-c`，再继续下一项。

| 场景 | 更新报告 / 实际资源状态 | 实际成员、选择和链路 |
|---|---|---|
| HTTP 401 | 退出 0，错误文字，ready=true / error 非空 | 保留 A/B/C，仍选 C，链路 p0-c + 前置 |
| HTTP 403 | 同上 | 同上 |
| HTTP 404 | 同上 | 同上 |
| HTTP 500 | 同上 | 同上 |
| HTTP 503 | 同上 | 同上 |
| 连接重置 | 退出 0，NSURLErrorDomain -1005；一次命令触发 6 次下载请求 | 保留 A/B/C、C 选择和链路 |
| 响应截断 | 退出 0，-1005；实际 Content-Length 未满足，2 次下载请求 | 保留 A/B/C、C 选择和链路 |
| 服务不发送响应 | 退出 0，-1001 超时；2 次下载请求，总观察约 12.86 秒（含 0.8 秒读回稳定等待） | 保留 A/B/C、C 选择和链路 |
| HTTP 200 空内容 | 退出 0，“服务器未返回任何数据。”，error 非空 | 保留 A/B/C、C 选择和链路 |
| 只有坏节点定义 | 退出 0，“Failed to parse remote resource data”，error 非空 | 保留 A/B/C、C 选择和链路 |
| 有效 A/B + 坏 C | **success，error 为空** | **只载入 A/B；C 消失，选择转 REJECT，合成链路请求被拒绝（503）** |
| 重复 C，第二条用户名不同 | **success，error 为空** | A/B/C 各一项；仍选 C；实际采用第一条 p0-c，第二条 p0-b 未生效 |
| 同名 C 参数替换 | success | 仍选 C；C 的策略标识改变，组请求与独立探测均实际转为 p0-b + 前置 |
| 删除未选中的 C | success | 恢复 A/B，REJECT 保持，合成链路请求被拒绝（503） |
| 删除正选中的 C | success | 恢复 A/B，选择自动转 REJECT，合成链路请求被拒绝（503） |
| 资源服务停止监听 | 退出 0，-1004 无法连接服务器；没有请求到达服务 | 旧 A/B/C 和选中 C 继续工作 |
| 资源服务重启但未初始化（503） | 退出 0，503 错误 | 不重放旧候选；Surge 自身缓存仍保留 A/B/C 和 C 链路；显式恢复有效基线后更新成功 |

以上“删除后 REJECT”只是在 **REJECT 为此测试组首项**的条件下得到，不能推广为任意组的默认安全行为。重复名“第一条生效”也只代表本次输入顺序。服务停机/重启测试针对本机资源监听器；没有重启 Surge 或 Mac，没有测试突然断电。

## 代码发现与回归

将真实的“资源服务器无法连接”输出交给现有 CLI 适配器，复现错误分类：退出 0 的 `<key>: 无法连接服务器…` 被泛化的无法连接匹配器提前解释为 `SURGE_UNREACHABLE`。实际是资源下载失败，Surge 控制器仍可响应，旧节点仍工作。

修复仅将**退出 0、恰好一行、匹配本次请求 key**的资源更新 stdout 交给严格资源结果解析器；非 success 仍抛出 `SURGE_COMMAND_FAILED`。stderr、真正控制器断连、其它 key、多行提示、其它原语仍按原规则拦截。新增 10 个真实错误样本和 4 个控制连接保护用例。修复前 1 个回归失败，修复后针对适配器及故障夹具的 112 项通过。

故障夹具独立于原型，只接受有限合成场景，不接受任意响应内容或文件路径。49 项回环相关测试与 P0 TypeScript 检查通过（Node 24.19.0）。独立修复 [PR #13](https://github.com/ElijahRRR/safari-profile-surge/pull/13)，提交 `39fa26d49b5c32937783ac309daae32f218ac343`：类型检查、构建、598 文件仓库扫描通过；默认并行全量检查有 7 个超时，不提高超时阈值、改为 2 个工作进程后，143 个测试文件、3989 项通过、1 项跳过。原型分支已纳入同一修复；未把源码修改部署到运行中的产品应用。
