# 方案 1：场景驱动 Safari 代理——设计稿

日期：2026-10-21，Asia/Taipei。状态：方案设计，不代表功能已实现。没有导入真实账号、安装宿主或修改当前 Surge 配置。

本稿采用用户最新澄清：首次准备、日常使用、登录处理不是每次必须串行执行的一条流程。已经登录的账号直接打开订单页；只有页面实际要求登录时才填充。

## 1. 使用方式与边界

目标：用户或 GPT 根据本机文件建立环境。每个环境关联一个 Safari 用户场景、一条出口代理（一般 SOCKS5，必须带前置代理）、一个 Amazon 买家账号和站点。日常打开该环境时，Safari 自动使用关联出口，Chrome 保持原有规则。

推荐产品由 Safari 扩展、最小 macOS 原生宿主和本机后台服务组成，作为同一安装包交付。管理界面采用类似 Sub-Store 的本机网页，用户主要操作网页和插件弹窗；后台统一负责配置、凭据和 Surge 控制。网页关闭后后台仍工作。

具体接口、实时事件、并发控制、网络验证和回滚，见 [实时同步设计](插件-网页后台-Surge实时同步设计.md)；固定日常配置、统一命名和变更生效方式，见 [固定工作配置设计](固定工作配置-命名与更新机制.md)。

**方案 1 的范围是整个 Safari 在同一时刻共享一个出口。**因此已配置场景 A、场景 B、未配置场景不能同时各走不同策略。“未配置场景走 Surge 原规则”适用于进入普通模式、没有其他托管环境占用 Safari 时。两个不同环境同时打开，必须进入冲突处理，不能按前台窗口悄悄争抢代理。

第一版建议只允许一个环境处于使用状态；同一环境的多个窗口可以共用出口。Chrome 可以同时正常使用。对于切换后旧环境的后台请求，不能仅靠窗口失焦来假定其已停止。

## 2. 三组相互独立的流程

### 2.1 首次准备或修改

导入文件 / 手动添加 → 建立环境记录 → 生成并校验 Surge 节点 → 创建或关联 Safari 场景 → 启用扩展并确认绑定。

这些动作只在新增或修改时执行，不在每次访问订单页时重做。可以先批量建立代理和环境记录，再分批完成 Safari 场景关联；进度逐项保留，重试只补未完成项。

### 2.2 日常使用已有环境

打开已绑定场景 → 判断是否已经使用正确出口 → 必要时切换并验证 → 打开或定位订单页。

同一环境已经处于使用状态时，不重建配置、不切换到同一个代理、不强制重新登录、不因打开弹窗刷新订单页。失焦到 Chrome 不释放 Safari 当前环境。

### 2.3 登录页条件分支

订单页正常显示 → 结束，不调用填充功能。

订单页跳转到该站点的登录页 → 验证当前场景和出口仍正确 → 按当前登录步骤填充关联账号或密码。

没有可用凭据、域名不符、场景冲突、出口未确认时，不填充。只填充，不自动提交登录、不处理验证码或二次验证。登录完成后由站点回到订单页；必要时提供“返回订单”按钮，不反复重定向。

## 3. 导入文件与数据关系

建议支持 CSV/XLSX，另提供给 GPT 或脚本调用的 JSON 格式。最终均进入同一本地管理服务，不让 GPT 直接拼接 Surge 密码行。

| 字段 | 要求 | 处理 |
|---|---|---|
| environment_id | 首次可空 | 首次生成稳定 ID，之后用于更新和去重；名称不是唯一身份 |
| 环境名称 | 必填 | 展示名称，建议与 Safari 场景名称一致，重命名不改变绑定 |
| 代理类型 | 可默认 socks5 | 先支持 socks5；其他类型单独适配 |
| 代理地址、端口 | 必填 | 连接入口，不能直接当作实测出口 IP |
| 代理用户名、密码 | 依节点要求 | 在本机读取，日志和导入结果不返回明文 |
| 前置代理引用 | 可用全局默认 | 首次安装选择本机已有前置节点；每行可覆盖 |
| Amazon 站点 | 必填或导入时统一选 | 决定订单地址、登录域名和填充范围，不默默假定美国站 |
| 买家号标识/备注 | 可选 | 用于展示和定位，未必等同于登录账号 |
| 登录邮箱/手机号、密码 | 可选 | 有登录需求时使用；缺失不阻碍已登录场景打开订单 |
| 预期出口 IP | 可选 | 用户提供时用于核对；不提供则通过验证建立观测基线 |
| 自动打开订单、登录页自动填充 | 环境选项 | 前者默认开启；后者在配置了凭据并启用后生效 |

内部关系：environment_id → 本机 Safari profile identifier → proxy_id → front_proxy_id；account_id 与环境关联，密码单独存储。

同名环境有冲突时提示选择“更新已有 / 新建”，不猜测覆盖。重复导入相同 ID 和相同内容是无操作；代理变化不重建 Safari 场景，不清 Cookie；账号变化也不删除已有登录状态。若修改了关联账号但页面仍登录旧账号，显示“配置账号已更换，网页登录状态未核对”，不把配置值当作页面实际身份。

导入只解析数据，不执行工作簿宏、公式、外部链接或文件中的命令。验证端口、协议、前置引用及链路循环；用受控序列化生成 Surge 配置，处理凭据中的逗号、引号等字符，拒绝无法安全表达的内容，不能直接把表格文本拼进规则。

批量执行返回：就绪、代理不可用、待创建场景、待启用扩展、待关联、同步失败等独立状态。一个环境失败不撤销其他成功项，但绝不把失败项标为可启动。

## 4. 创建 Safari 场景与第一次绑定

必须区分产品里的“环境记录”和 Safari 自己的“用户场景”。创建记录很容易，但不能据此声称 Safari 场景已创建。

Apple 官方说明新场景的扩展默认关闭。插件不能在自己尚未启用的场景里自行启用自己；因此“所有场景默认装上”应实现为安装一次、创建向导统一检查各场景启用状态，新场景漏启用时提示补齐。不能承诺安装一次后所有未来场景自动获得授权。[Apple 场景说明](https://support.apple.com/en-us/105100)

建议第一次绑定：

1. 导入后生成待关联环境列表。
2. 通过 Safari 官方界面创建指定名称场景，或选择现有场景。
3. 在该场景启用扩展并打开弹窗；弹窗列出待关联环境。
4. 用户选择一次环境，扩展通过 native messaging 将真实场景标识发给本机应用，记录绑定。
5. 后续只依据稳定场景 ID 找环境；显示名称可改，不按窗口标题或模糊名称猜测。

Apple 提供 SFExtensionProfileKey 用于消息中的场景身份；此前本机实验也确认每个场景有独立扩展实例与存储。需在正式原生宿主中验证该标识的读回、重启和重装生命周期。[SFExtensionProfileKey](https://developer.apple.com/documentation/safariservices/sfextensionprofilekey) · [Apple 扩展场景模型](https://developer.apple.com/videos/play/wwdc2023/10119/)

**批量创建及按 ID 打开指定场景，尚未确认存在可直接使用的公开 API。**设计应先验证官方支持能力；不足时提供官方 UI 创建向导，或在获得系统权限后以可核对的界面自动化辅助。不能直接写 Safari 私有数据库，也不能把自动化点击当成长期稳定 API。GPT 可以通过相同导入服务及官方界面完成，不另走一条未经核对的写入路径。

临时文件夹扩展不适合作为日常产品：退出 Safari 会移除，也不承载所需原生宿主。正式版需要打包、签名及正常安装流程。

## 5. Surge 规则设计

目标：保留用户原有配置和 Chrome 行为。环境数量增加时增加节点，不按每个网页、资源或账号生成请求头规则。Amazon 不需要本项目新增 MITM。

首次备份本机原配置，以其副本建立固定的日常工作配置（建议名“日常-Safari环境”），之后平常上网和 Safari 环境共用这一份配置，不再随环境切换配置文件。原始备份只用于恢复。保留原节点、组、规则和模块；本应用只拥有带固定前缀和记录 ID 的新增部分。配置变更从当前有效基线生成，记录版本与摘要；发现用户或订阅更新时重新合并，不用陈旧副本覆盖。无法无歧义合并时停止同步并显示差异。

受管理部分包括：

- 每个环境一个出口节点，如 SFE-N-E0001-US01-v003，带显式 underlying-proxy 引用。
- 一个固定的 Safari 专用 select 组 SFE-ROUTE，首个成员固定为 REJECT，然后是有效环境节点，不加入 DIRECT 或自动 fallback。
- 经实测确认的 Safari 进程完整路径匹配条目。不能只写通用 com.apple.WebKit.Networking；Chrome 不匹配这些路径。
- 切换期间阻止 Safari 新连接的受管理入口，以及解除托管时移除/停用该入口的机制。

示意结构，不可直接导入：

```text
出口节点 E：SOCKS5 地址/凭据 + underlying-proxy=指定前置节点
Safari 专用组：select(REJECT, E1, E2, ...)
托管时：经过验证的 Safari 进程路径 → Safari 专用组
普通模式：Safari 专用入口不生效 → 继续匹配原有完整规则
Chrome：始终不命中上述入口 → 原有完整规则
```

`underlying-proxy` 的链路方向是本机 → 前置代理 → 环境 SOCKS5 → 目标网站。所有环境必须有可解析的前置引用；不能缺失时悄悄直连 SOCKS5 服务。前置优先使用固定节点；若使用原有可切换组，须验证当前 Surge 版本支持及变更影响。[Surge SOCKS5](https://manual.nssurge.com/policies/socks5.html)

**普通模式不是把专用组切成 DIRECT，也不是复制原 FINAL 策略。**用户原有规则可能包含域名、地区、广告和其他条件，必须让请求真正继续使用整套原规则。持久条目启停或本机 CLI 的精确临时规则管理需先实测优先级、持久性与回滚，不能假设存在“继续原规则”的特殊策略。

对代理同步：本机应用串行生成候选节点资源 → 官方 CLI 校验及逐节点检查 → 通过能力门槛后定向发布 → 读回成员/错误/组选择 → 记录部署版本 → 实际请求验证。优先使用 policy-path 独立资源；本机 6.5 的定向刷新无中断行为尚未实测，未通过则显示待部署，不自动重载。新增前置/组等主配置结构变化在受控维护中合批处理；同一配置 reload 也不保证无影响。模块不用于添加普通节点/代理组。

日常切换环境只更新专用组选择，不重写整份配置。普通/托管模式切换涉及启停入口，优先验证精确运行时规则管理，不允许为每个状态默认重载主配置；临时规则读接口可用不代表写入/优先级已通过。后台心跳及失焦事件不得选择代理，只有受理的新环境激活事务能改变出口。[Surge 进程规则](https://manual.nssurge.com/rules/process.html) · [组选择接口](https://manual.nssurge.com/tools/http-api.html) · [select 默认成员行为](https://manual.nssurge.com/policy-groups/select.html)

## 6. 实际控制：如何避免首个请求和旧连接走错

这是上线前的首要验证点。不能用“插件发现页面已加载，再切代理”作为正确流程。

推荐第一版提供应用菜单中的“打开环境”和每环境启动入口，GPT 也调用同一入口。该入口提前知道 environment_id，在 Safari 加载 Amazon 之前完成切换。是否能顺利打开指定 Safari 场景需要第 4 节的能力验证；未通过时使用已绑定场景的空白准备页引导，不能伪称一键自动完成。

激活事务：

1. 当前已是同一环境且配置版本正确：复用，不重复切换；已有订单页就定位它。
2. 不同环境：检查其他 Safari 场景/窗口和现有连接，进入切换中；仅阻止 Safari 新连接，Chrome 不变。
3. 处理旧环境。关闭或保存旧环境窗口必须有明确的产品设置；有未提交表单时暂停。仅最小化/失焦不算停止其网络活动。
4. 只结束确认属于 Safari 的旧连接，避免 keep-alive、H2、WebSocket 继续使用旧出口；不清空 Chrome 连接。
5. 验证前置与目标 SOCKS5，选择新环境节点，读回 Surge 状态。
6. 打开目标场景的准备页，确认其 native profile identifier 与目标相符，再允许它发出口检测请求。
7. 由该场景实际发请求，核对浏览器出口和 Surge 策略；成功后打开或定位订单页。
8. 跳到登录页才进入填充分支；已经登录就保持现状。

如果无法证明关闭旧窗口后旧场景的后台请求已停止，第一版采用“保存工作后退出并重开 Safari”作为跨环境切换后备方案；不自动清 Cookie，不默认能恢复所有会话或未提交表单。是否必须重启，应由实验决定，不把重启作为每次打开订单的固定步骤。

### 直接从 Safari 菜单打开场景

可作为目标体验：扩展发现新窗口后报告场景，本机应用激活出口，再打开订单。但新窗口恢复标签页、扩展启动时序、未启用扩展、从普通模式首次进入代理场景，都可能在通知前发网络请求。

因此第一版不能同时承诺“任意原生入口直接打开”“毫无额外准备”“首包绝不走旧出口”。先实现可控入口；原生菜单自动接管只有在空白启动、后台拦截及启动时序测试通过后启用。若用户绕过可控入口恢复既有 Amazon 标签页，应明确显示本次打开未经启动验证，而不是显示虚假的绿色状态。

### 未配置场景

没有托管环境活动时，未配置场景走原规则；无需填写代理，也不自动跳订单。

托管环境使用期间再打开未配置场景，会触发冲突。不能一边让整个 Safari 走 A，一边承诺这个未配置窗口仍走原规则。推荐提供“结束当前环境，进入普通模式”操作，先处理旧窗口/连接再撤销专用入口。用户只需切换一次模式，不手改 Surge。

## 7. 实际 IP 与插件弹窗

必须区分三个字段：代理连接地址、预期出口、当前场景实测出口。三者不一定相同。

本机辅助程序对指定代理发起的预检只证明该代理能用；它不能冒充当前 Safari 的实际出口。实际出口由当前场景的验证页发请求获取，并与 Surge 中同一次连接的进程、策略核对。检测页只请求独立 IP 服务，不把 Amazon URL、买家号或密码发送给该服务。

第一次激活、切换代理、网络变化和检测过期时重测；普通弹窗打开可读最近结果并展示时间，不每次切代理。失败显示“未确认/上次结果”，不将缓存 IP 标为实时。用户填写固定预期 IP 时不符则停止自动打开订单；代理连接地址不能自动作为预期 IP。

弹窗示意：

```text
环境：US-买家01                 状态：使用中
绑定场景：US-买家01
买家号：buyer01@example.test    页面登录状态：未核对/已识别
站点：Amazon US
代理：SOCKS5 203.0.113.10:1080
前置：已配置的前置节点
实际出口：检测结果             检测时间：刚刚/xx 秒前
Surge：已同步 / 切换中 / 同步失败

[打开或定位订单页] [重新检测] [编辑]
```

这里的 IP/账号是布局占位，不是真实配置。代理密码、买家号密码不直接展示。页面登录身份只有在有可靠页面证据时显示“已识别”，不能以存储的绑定账号替代。

未绑定场景显示“当前场景未绑定”，提供“关联已有环境”和“在此创建环境”；不按场景名称自动套用另一个买家号。

## 8. 手动添加和修改

插件“编辑”调用同一个本机管理服务：修改环境展示名、代理、端口、代理凭据、前置引用、站点、买家号信息。敏感字段可在宿主编辑窗口完成，弹窗保存后刷新状态。

- 修改非当前环境代理：生成新版本、验证并同步节点，当前 Safari 出口不切换。
- 修改当前环境代理：保存为待应用版本；执行受控切换，处理旧连接并重新测出口。成功才显示新 IP 已生效。
- 修改买家号信息：更新凭据绑定，不改代理规则、不强制登出；已经登录的网页不会因为改配置而自动换成新账号。
- 修改场景名称：保留 ID 绑定；Safari 显示名称是否同步另行处理，不用名称做路由键。
- 修改前置节点：列出受影响环境，批量验证；当前活动环境按切换事务处理，失败项保留状态。
- 解除绑定：先退出活动环境，再撤销映射；不删除 Safari 场景、Cookie 或账号登录资料。

界面区分“已保存”“已同步到 Surge”“当前已使用”，避免文件保存成功但网络没变的假成功。导入与手动编辑使用版本检查，GPT 和用户同时改动时不覆盖彼此。

## 9. 账号填充与本机数据

登录填充是单独的页面功能，不参与一般网络规则，也不是打开订单的必经步骤。

仅对该环境配置站点的明确 HTTPS 登录页面启用；核对顶层页面来源、表单目标以及当前环境版本，不向第三方 iframe 或相似域名填入凭据。支持邮箱页和密码页分步出现；只有出现对应字段才填。页面结构变化时显示可手动填充，不猜测提交按钮。

Safari 自带的 Passwords/AutoFill 信息是跨场景共享的，因此不能以“Safari 场景隔离”假设系统密码库也按场景隔离。方案应在本机 Keychain 保存按 environment_id/account_id 关联的凭据引用，避免依赖 Safari 自动选中哪个账号。[Apple 场景说明](https://support.apple.com/en-us/105100)

账号密码放 Keychain，普通数据库只放引用；扩展不在 localStorage/storage.sync 保存密码。仅在已验证的登录页面需要填充时短暂传递相应凭据。新应用使用系统正常安装和访问授权，不能绕过 Keychain 提示。

代理密码同样可保存在 Keychain，但 Surge 节点配置本身通常需要可读凭据，所以生成的本机 Surge 配置仍是敏感文件，不能宣传为“所有密码永不落盘”。限制本机文件访问、排除日志和公开包，记录必要备份的保留规则。导入原文件不擅自删除或上传；GPT 默认获得脱敏结果和记录 ID，避免把密码放在命令行或对话。

## 10. 异常与产品状态

| 情况 | 预期行为 |
|---|---|
| 新环境未关联 / 扩展未启用 | 待完成状态，不自动打开该账号订单页 |
| 代理或前置不可用 | 本次激活失败，不自动换其他买家环境或 DIRECT |
| 选择组成功但浏览器 IP 未确认 | 保持“验证中/失败”，不宣称就绪 |
| 原配置/订阅发生变化 | 对照新基线合并，仅修改本应用管理部分，冲突时停同步 |
| 多环境争抢 | 按显式激活请求串行处理，旧请求结果不能覆盖新请求 |
| 窗口切到 Chrome | 不切换或释放 Safari 出口 |
| 插件或宿主退出 | 不自动改成 DIRECT；保留已应用策略，但不能假定宿主故障后仍能自动阻止所有请求 |
| Surge 被关闭或接管关闭 | 停止自动启动、填充并告警；没有独立系统级防火墙时，不承诺进程仍在却永不直连 |
| Safari/macOS 升级改变进程路径 | 重新验证归属；不能扩成通用 WebKit 规则以“修复” |
| SOCKS5 不支持 UDP | 验证拒绝或明确处理 Safari UDP，不静默走原出口；网页 H3 的降级与可用性要实测 |
| DNS、系统服务、原生 IPv6 | 单独列明归属和覆盖，不能将进程规则说成系统级全部流量隔离 |

“锁定 Safari/阻止请求”均为待实现并实测的控制行为，不是目前代码已经提供的能力。方案的账号使用体验不等于指纹隔离或账号关联风险保证。

## 11. 建议实施顺序与验收

第一轮只验证控制核心，用空白测试场景与 IP 回显页，不导入买家账号：

- Safari 的 HTTPS、H2、UDP/QUIC 与其他相关网络进程是否可准确匹配；Chrome 访问同一目标不受影响。
- 前置 + SOCKS5 的真实出口；只切专用组而非原通用组。
- 普通模式是否真正继续原规则，不是改成 DIRECT。
- 切换时新请求被拦住、旧连接停止、首次 Safari 请求已走新出口。
- native profile ID 获取及跨启动稳定性；批量创建/启用扩展/按场景打开的实际自动化边界。
- 原生菜单直接打开、恢复标签页、启动时宿主未就绪等最差时序；过不了则采用受控入口并清晰标注。

新增前置验收：固定工作配置在整个日常流程中不切换；新增/修改节点的定向发布不重置其他应用连接；未通过则禁止自动部署。命名冲突、外部资源跳过坏行、当前选中节点丢失、自动重载及外部编辑需分别测试。

第二轮实现本机导入、环境记录、Keychain、手动编辑、Surge 同步和失败回滚。第三轮完成订单页自动打开、登录页条件填充及弹窗展示。最后再优化批量创建和日常启动步骤，不先承诺绕过 Safari 授权的一键全自动。

最低交付应包含：可安装宿主与扩展、CSV/XLSX 模板、受控启动入口、脱敏 CLI 导入/查询接口、配置差异预览、真实请求证据、卸载与回退说明。首次安装及场景启用后，正常日常操作目标是一键打开环境，其余自动完成；已登录账号不经过登录流程。

待确定的产品选项：具体 Amazon 站点、默认前置节点、跨环境切换时是否允许保存并关闭旧 Safari 窗口、无法可靠暂停旧环境时是否接受重开 Safari。它们不影响本稿的架构，但会影响最终操作体验。
